# 不足与展望（论文素材版）

> 用途：毕业论文「系统不足与未来工作」章节的直接素材。每条都给出：不足是什么、
> 为什么是**有意的取舍**（而非疏漏）、以及后续工作方向。与 `docs/known_issues.md`
> 的工程条目一一对应（标注 KI-#）。写论文时可按四个维度分节展开。

## 一、数据与语料层

**1. 演示语料是合成映射（最重要的诚实声明）。**
线上检索语料由 31,879 条真实 LinkedIn JD 经确定性变换而来：JD 正文保留英文原文，
公司/城市按策展池映射为中国（70%）与英国（30%）实体，签证担保字段按国别比例合成，
薪资不做任何伪造。全链路带 `demo_synthetic` 标记（数据库列 → API 字段 → 前端徽章），
发布门校验缺失标记即拒绝发布。
*展望*：接入真实且授权可用的招聘数据源（官方 API 或合作渠道），语料切换机制
（advisory-lock 围栏 + 快照回滚）已就绪，可直接复用。

**2. 中文 UI 与英文 JD 的跨语言鸿沟。**
用户用中文咨询，JD 是英文：目前依赖 Qwen embedding 的跨语言能力与咨询引擎生成的
英文 `title_keywords` 补偿，BM25 通道对中文查询贡献有限。
*展望*：查询翻译层或双语查询扩展；对照实验量化跨语言损失。

**3. 案例库双模型未打通（KI-1/2/5）。**
写入链（`career_cases`）与隐式检索读取链（`anonymous_resume_cases`）是两套表，
反馈沉淀的软偏好尚无排序消费方。P1 阶段以机制演示为目标（seed_cases 走通流程）。
*展望*：统一案例数据模型，让历史成功案例真正参与排序加权，并做消融验证收益。

## 二、检索与评估层

**4. 评估标注的口径差异。**
原始评估集（arshkon 1000 岗、15 查询、人工标注）与演示语料是两个数据集，标注岗位
在新语料中命中为零。因此新语料上的指标采用 TREC 池化 + LLM 评审标注
（`scripts/evaluate_demo_corpus.py`，产物在 `data/eval/demo_corpus_v1/`）：
池化 Recall 是"池内召回"偏乐观，LLM 标签与人工标签不可横向比较——两组数字在论文中
必须分开呈现、注明口径。
*展望*：对 LLM 标注做人工抽检（估计一致率）；扩大查询集；引入分层抽样的人工标注子集。

**5. Cross-encoder 精排仍是预留接口（P2）。**
主线排序止于 bi-encoder 余弦相似（查询向量 × 岗位块向量独立编码后点积）。
Cross-encoder 把"查询+JD"拼成一个输入过模型打分，能建模词级交互、显著提升 Top-20
的排序质量，但每对都要过一次前向、延迟与成本高一个数量级，故按范围纪律留作 P2。
*展望*：Top-20 之后接 bge-reranker 类模型做精排，用现有评估管线量化 NDCG 增益。

**6. RAPTOR 层级树为消融配置，未进主线服务。**
RAPTOR-lite（岗位摘要节点 + 角色簇汇总节点，确定性摘要 + 向量化）已实现并可通过
`include_raptor` 开关参与检索；代际清理与角色节点白名单越权两个缺陷已修复。
主线默认关闭：额外一跳节点检索增加延迟，收益需评估证明。
*展望*：以消融数字决定是否入主线；探索真正的多层聚类摘要树（当前为两层轻量版）。

**7. 硬过滤词表依赖离线入库质量。**
`role_cluster` 等受控词表在入库时由 LLM 归类，归类错误会让相关岗位被硬过滤挡掉，
线上无从发现。
*展望*：词表归类抽样审计；对零结果查询做"放宽过滤重试"的可解释降级。

## 三、认证与产品层

**8. 短信通道未接真实网关（KI-12）。**
双通道 OTP 架构完整（限流、防遮蔽、防枚举），但手机侧只有 console/disabled 两个
provider；生产模式强制要求至少一个真实通道（SMTP 已实现）。
*展望*：接入腾讯云/阿里云或聚合商短信 API（provider 接口已预留，预计 <100 行）。

**9. 账号删除与数据保留策略未交付（KI-11/13）。**
删除需按 checkpoint → run → session → memory → identity 的依赖顺序编排，且历史
无主数据（W3 之前的会话）不能靠猜测归属。当前策略：无主数据在鉴权模式下一律不可达。
*展望*：受审计的认领流程 + 到期删除策略 + 单端点级联删除编排。

**10. 支付与配额只做了产品壳。**
每账号 3 会话额度与付费墙弹窗已上线，但"升级额度"按钮是占位——无支付通道。
*展望*：接入微信/支付宝（个人主体可走服务商模式），配额表迁移到独立账务模型。

## 四、工程与运维层

**11. 任务执行是进程内 BackgroundTasks（KI-10）。**
重启会丢正在执行的 run（已有启动时 stale 回收把它们标记失败，用户可重试）。
单机演示够用；多实例部署需要真正的任务队列。
*展望*：RQ/Celery + Redis，或 PostgreSQL SKIP LOCKED 队列（改动面最小）。

**12. 可观测性偏薄。**
监控读模型（运行统计、阶段耗时）已有，但应用日志稀疏、无分布式追踪。
*展望*：结构化日志 + OpenTelemetry；LLM 调用的 token/成本记账。

**13. 演示部署形态的边界。**
本机单实例 + `AUTH_COOKIE_INSECURE` 局域网演示开关（production 拒绝）。公网部署
需要 https、域名与备案（大陆节点）或境外节点，及每用户成本闸门（配额已有）。
*展望*：docker-compose 一键部署 + Caddy 自动 https；水平扩展依赖 §11 的队列改造。

**14. 评估与运行时共享一个数据库实例。**
评估脚本直接跑在服务库上（读为主，judge 结果落文件不落库），答辩演示与评估并发
执行会互相争抢 embedding 限流额度。
*展望*：独立评估环境或只读副本。

---

### 给答辩的一句话总结

以上不足分为三类：**有意的范围取舍**（P2 项、支付、短信）、**诚实的方法论边界**
（合成语料、LLM 标注口径）、**工程化的下一步**（队列、可观测性、部署）。所有取舍
都有书面记录与预留接口，没有一条是"不知道"，只有"知道但按一个月范围纪律排在了
主线之后"。
