# 模块一：简历归一化与证据链

## 概述

用户上传的简历往往是 PDF、DOCX 或文本文件。版式、栏目名和写法各不相同，不能直接作为后续检索和生成的稳定输入。本模块先抽取原文，再把教育、经历、项目、技能和质量问题整理进统一状态。

“归一化”就是把不同格式、不同写法的简历整理成相同的数据结构。它不是重写简历。系统先保存原文证据，再允许模型做结构化理解。因此，后续建议既能使用统一字段，又能回到用户原文核对。

## 目标

- 接受完整简历文件，而不是要求用户逐项填写一张“经历事实库”表单。
- 为每项结构化事实保留可追溯的原文片段，形成 `R###` 证据编号。
- 把排版、内容缺失和表述含糊等问题整理成结构化质量信号。
- 让用户在咨询前预览并确认当前简历版本。
- 防止旧上传任务晚到后覆盖新简历，或让旧确认继续生效。

## 用户交互与数据流程

1. 用户在群聊工作台上传简历。接口先登记一次新的上传尝试，立即把旧确认作废，并把处理状态设为排队。
2. 后台任务抽取文件文本。PDF 保留页码线索；DOCX 读取段落和表格；文本文件按编码回退读取。
3. 系统在调用大模型前切分原文，生成 `R001`、`R002` 等证据片段。每个片段保存原文和可用的页码。
4. 归一化模型输出教育、经历、项目、技能和质量问题，并为结构化事实引用证据编号。本地校验只接受已存在的 `R###` 编号，并剔除无法由所引原文支持的事实项。
5. 系统把普通质量问题同时整理为带严重级别、字段路径和证据编号的结构化问题。它们是下一模块判断是否需要追问的输入。
6. 处理成功后，前端展示简历档案、质量提示和原文证据。用户可以确认当前版本，也可以重新上传；当前实现不是让用户在表格中直接改写模型输出。

这里有两个容易混淆的生命周期编号。`generation` 表示“第几次上传尝试”，上传一被接收就变化；`resume_version` 表示“第几份成功写入的归一化简历”，只有当前上传成功后才变化。后台保存成功或失败前都要核对 generation。旧任务发现自己已经过期时放弃写回。用户确认时再核对当前 version，从而把“上传接单”“归一化完成”“用户确认”分开管理。

## 技术组成

- `app/normalization/resume_intake.py`：文件解析、原文压缩、`R###` 切分、结构化归一化、事实与证据一致性校验、质量问题整理。
- `app/state/schema.py`：`ResumeState` 的单一数据契约，保存结构化简历、原始证据、质量问题和后续澄清字段。
- `app/db/state_store.py`：按 `session_id` 保存状态，并在行锁事务中管理 generation、version 和确认状态。
- `app/api/v1/sessions.py`：上传、后台归一化、预览和确认接口；耗时处理采用“接单后轮询”而不是让一次 HTTP 请求长时间等待。
- DeepSeek 异步客户端：负责结构化理解；调用统一经过 Semaphore 限流。模型返回后仍要经过本地证据校验。

## 工程创新点

第一，证据建立早于模型结构化。模型不能自行创建一个看似合法的证据编号，结构化事实必须引用系统已经切出的原文片段。

第二，generation 和 version 分工。它们把并发上传中的“任务新旧关系”与“用户确认哪一版”拆开，解决旧任务晚到和旧确认短暂复活的问题。

第三，质量问题不只是一段提示文字。结构化的字段路径和严重级别可以直接成为澄清回路的确定性输入，连接归一化与咨询两个模块。

## 完成标志

- 支持的简历文件能够抽取出非空文本，并生成稳定的 `R###` 证据。
- 教育、经历、项目、技能和质量问题能够写入同一份 `ResumeState`。
- 结构化事实引用的证据编号都来自当前简历；不受支持的事实不会进入有效状态。
- 新上传会使旧确认失效；过期后台任务不能覆盖当前结果。
- 用户能够看到当前档案与证据，并明确确认当前版本后再进入咨询。

# 模块二：简历澄清回路

## 概述

归一化可以识别“这段经历缺少成果”“这个项目没有写使用的技术”，但不能替用户补写事实。直接把这些缺口交给后续模型，会在简历建议阶段留下编造风险。本模块把质量信号变成有上限、可跳过、可追踪的澄清问题。

`resume_clarify` 是咨询状态机中的一个阶段。它只在基础求职槽位已经补齐、当前简历确有待处理目标、功能开关开启且仍有预算时出现。没有目标时，系统不会为了展示功能而凭空追问。

## 目标

- 把归一化发现的含糊点转成针对具体字段的问题。
- 确保用户回答只补到上一轮真正询问的目标上。
- 把有效回答保存为用户原话证据，而不是模型改写后的“新事实”。
- 支持跳过当前目标或剩余目标，不强迫用户披露不愿提供的信息。
- 让新增证据进入本人显式匹配与策略链，同时不直接进入匿名案例查询。

## 用户交互与数据流程

1. 归一化阶段按确定性顺序选择澄清目标：先看高、中优先级质量问题，再看经历是否缺职责或成果，最后看项目是否缺技能。目标数量受配置限制。
2. 咨询引擎先补齐目标方向、地点或远程意愿、签证需求等必需槽位。满足基础条件后，若仍有开放目标，则阶段切换为 `resume_clarify`。
3. 系统每次只问一个目标。发问时同时保存 pending 锚点。pending 的白话含义是“记住上一轮问的是哪一段经历、在哪一轮问、基于哪版简历问”。核心字段包括 `target_ref`、`asked_round` 和 `baseline_version`。
4. 下一轮收到用户消息时，系统先核对 pending 与当前简历版本。用户给出实质回答时，目标转为 answered，原话逐字保存为 `C###` 证据，来源标记为 `user_clarification`；用户选择跳过时，目标转为 skipped。两种情况都会清除当前 pending。
5. 模型可以给出简短摘要，但摘要中的有效内容必须能从用户原话提取。若摘要校验不通过，系统仍保留原话，不把摘要升级为事实。
6. 当前目标消费完成后，状态机选择下一个开放目标；目标耗尽后进入深挖或整理确认单阶段。

有效证据通过统一视图进入后续模块：`effective_resume_text` 把已确认的 `C###` 加到显式检索文本；`all_resume_evidence_spans` 把 `R###` 与 `C###` 一起提供给 Strategy Agent 和 Supervisor。这样，消费者不必各写一套拼接规则。

## 技术组成

- `app/normalization/resume_intake.py`：从结构化质量问题生成澄清目标。
- `app/agents/consult_engine.py`：阶段判断、单目标提问、跳过识别、回答摘要校验和咨询轮次控制。
- `app/api/v1/sessions.py`：pending 的版本核对、回答或跳过闭环、`C###` 编号与并发合并。
- `app/state/resume_view.py`：原始证据与澄清证据的统一只读消费视图。
- `app/retrieval/implicit_search.py`：匿名案例查询白名单，只读取去标识后的教育、经历、项目和技能字段，不读取 pending 或澄清原话。

## 工程创新点

第一，问题与回答通过 pending 锚点绑定。系统不是看到下一条用户消息就猜它属于哪个字段，而是用目标、轮次和版本共同限定消费范围。

第二，回答以原话成为 `C###` 证据。模型摘要只是辅助表达，不能取代用户原话，也不能扩大事实范围。

第三，新增证据的消费边界是分层的：它可以服务当前用户的显式检索和简历策略，但不会直接拼进匿名案例空间的检索 query。这是一条具体的数据流边界，不是“绝对无隐私风险”的笼统承诺。

## 完成标志

- 有质量目标时能够进入 `resume_clarify`，无目标时不额外发问。
- 每个问题都带可持久化的 pending；跨轮或跨版本回答不会误写到旧目标。
- 有效回答生成 `C###`，且证据文本与用户原话一致；跳过动作有明确记录。
- `C###` 能被显式检索、策略生成和发布核查消费，但不会直接进入隐式案例查询文本。
- 冻结验收中的含糊简历演示路径已走通 `C001` 生成、结果引用和后续匹配闭环；对更多真实简历类型的收益待测。来源：`docs/validation/2026-08-07-batch9-acceptance.md`。

# 模块三：岗位库与入库管线

## 概述

检索系统需要的不是一堆临时粘贴的 JD，而是一套可过滤、可全文搜索、可向量检索、可回溯来源的岗位库。本模块负责把公开岗位数据转换为 `jobs` 主表和 `job_chunks` 检索块，并为每个块生成向量。

“JD chunk”就是把一条很长的岗位描述按字段拆成较短的检索片段。岗位标题、职责、必需技能、加分项和原始 JD 片段分别入库，检索命中时可以返回更精确的证据，而不是只知道“整条岗位大概相似”。

## 目标

- 让地点、签证、学历、经验、岗位类别和开放状态等硬条件成为可查询字段。
- 同时保留原始 JD，避免结构化过程丢掉重要上下文。
- 生成带字段来源的 JD chunks，并建立全文索引和向量索引。
- 让大批量导入可以分窗续跑，失败后不必从头开始。
- 对 CN/UK 演示语料持续标明合成字段，防止演示事实被误写成来源事实。

## 数据流程

1. 原始岗位记录先经过字段校验、规范化和去重。通用入库路径可以使用 DeepSeek 从 JD 中提取职责、技能、学历、经验和岗位类别；无法从原文支持的字段保留未知值，不补造。
2. CN/UK 演示语料使用独立转换脚本。公司、地点和签证是合成场景字段；标题和 JD 主体来自源记录。每条记录带 `demo_synthetic`、国家代码、语料标签和来源 metadata。薪资不生成展示区间。
3. 转换阶段生成 manifest，记录输入输出指纹、行数对账、碰撞报告、合成字段清单和 embedding 指纹。
4. 导入器按窗口处理记录。每个窗口先登记状态，再构建岗位行和 chunks，随后批量调用 Qwen Embedding。超时和暂时失败采用有界重试；已成功窗口在续跑时跳过。
5. 一个岗位被拆成 metadata、职责、必需技能、加分项和原始 JD 摘要等字段块。每个 chunk 同时写入文本、向量和全文检索字段。
6. 岗位与 chunks 在同一事务中提交。演示语料导入时先保持不可见，完成计数核对和 embedding 指纹核对后，再通过离线切换流程启用。

## 技术组成

- PostgreSQL `jobs`：保存岗位标识、标题、公司、地点、签证、学历、经验、岗位类别、开放状态、职责、技能、原始 JD 和演示来源字段。
- PostgreSQL `job_chunks`：保存 `chunk_id`、`job_id`、字段名、内容、pgvector 向量和全文检索列；HNSW 用于向量近邻搜索，GIN 用于全文检索。
- `scripts/load_jobs.py`：通用 JD 结构化与字段化 chunk 构造。
- `scripts/transform_jobs_cn_uk.py`：CN/UK 演示转换、确定性映射、来源 metadata 和 manifest。
- `scripts/import_cnuk_demo.py`：embedding 指纹冻结、异步有界 worker、分窗状态、事务写入和对账。
- `scripts/cutover_cnuk_demo.py`：拒绝活动 run 的离线切换、可见性核查和回退快照。

## 工程创新点

第一，岗位数据同时保留“可过滤字段、可检索块、原始 JD”三种形态。SQL、召回和解释各取所需，但都能回到同一 `job_id`。

第二，embedding 指纹把模型、维度、切分器和构建版本绑定在一起。续跑和切换前会核对指纹，避免旧向量与新 query 模型混用。

第三，演示语料的合成边界贯穿数据列、结果投影和前端水印。正式环境需要显式允许才可启用演示语料；合成公司、地点和签证不能被叙述为来源网站提供的事实。

## 完成标志

- `jobs` 的硬过滤字段、原始 JD 和来源字段能够完整写入并按 `job_id` 查询。
- 每条可用岗位能够生成字段化 chunks；向量维度与运行时 embedding 配置一致。
- 全文索引、向量索引和岗位外键关系有效。
- 中断后能够从未完成窗口续跑，成功窗口不重复处理；导入前后计数和指纹能够对账。
- CN/UK 演示岗位在数据库、API 和界面上持续带合成标记；薪资不被补造成展示事实。

# 模块四：混合检索与融合

## 概述

单一检索方法很难同时处理“必须在伦敦且提供签证”与“经历表达不同但能力相近”两类问题。本模块先用 SQL 得到绝对不能越过的岗位集合，再在集合内并行运行关键词、语义和可选层级摘要检索，最后按岗位融合并加权排序。

“混合检索”就是把多种找法组合起来。BM25 擅长找明确出现的技能和职位词；Dense 检索把文本变成向量，擅长找表达不同但含义接近的内容；RAPTOR 先检索岗位或角色摘要，再把摘要命中传播回原始 JD 块，用来补充更高层的主题召回。

## 目标

- 地点、签证、学历、经验、岗位类别、公司和开放状态先走 SQL 硬过滤。
- 关键词、语义和层级摘要通道可以并行，不让一条外部调用串住整条检索链。
- 先把 chunk 命中折叠到 `job_id`，避免同一岗位的多个片段挤占榜单。
- 用 RRF 融合不同通道的名次，避免直接比较不同量纲的原始分数。
- 在融合后加入字段重要性和软偏好，但不允许软偏好把已过滤岗位重新带回。

## 数据流程

1. 输入是已确认简历构建出的查询、Match Brief 中锁定的硬条件、软偏好和结果数量。
2. SQL 根据硬条件查询 `jobs`，生成 `allow_ids`。开放状态始终参与过滤；其他条件按用户确认内容拼接。若允许集合为空，检索立即返回空结果。
3. BM25、Dense 和按计划启用的 RAPTOR 在同一个 `allow_ids` 范围内并行执行。Dense 调用 Qwen Embedding 生成 query 向量，再通过 pgvector 查询相似 chunk。
4. 每路 chunk 结果先按 `job_id` 折叠，同时保留该岗位命中的 JD 证据编号和字段来源。RAPTOR 的摘要命中也必须传播回允许集合内的原始 chunk。
5. RRF，也就是 Reciprocal Rank Fusion，按“一个岗位在各路排第几名”计算融合分。它关注排名而不是硬拼 BM25 分数与向量相似度。
6. 融合候选再做确定性加权。加权项包括 RRF、关键词、语义或 RAPTOR、证据字段重要性和软偏好。所有分数与证据随候选保存，供后续精排和解释使用。

## 技术组成

- `app/retrieval/hybrid_search.py`：硬条件校验、SQL 允许集合、并行召回、chunk 折叠、字段证据合并和确定性加权。
- `app/retrieval/rrf.py`：按各通道名次做 RRF 融合。
- `app/retrieval/raptor.py`：离线摘要节点构建、在线摘要检索与叶子 chunk 传播。
- `app/retrieval/query_builder.py`：把基础简历和已确认的澄清证据构造成字段化 query。
- PostgreSQL 全文检索、pgvector HNSW 和 `asyncio.gather`：分别承担关键词召回、向量召回和通道并发。

## 工程创新点

第一，硬过滤先产生允许集合，后续每一条召回路径都显式接收这个集合。这样，语义相似不能替代签证或地点等不可违反条件。

第二，融合发生在岗位层而不是 chunk 层。它既减少重复岗位，又把真正命中的 JD 片段继续作为解释证据。

第三，RAPTOR 不是另一条绕开主线的候选来源。摘要命中必须回到原始岗位块和 `job_id`，并继续受同一允许集合约束。

## 完成标志

- 任一返回岗位都属于 SQL 允许集合，关闭岗位不会进入候选。
- 各检索通道可以并行执行，任一通道的输出都能折叠为岗位级排名。
- RRF 输出稳定的 `job_id` 排名，候选携带通道分数与 JD evidence IDs。
- 软偏好只影响允许集合内的次序，不改变硬条件结果。
- RAPTOR 开关关闭时走 BM25 与 Dense 基线；开启时只增加受约束的第三召回通道。

# 模块五：精排与双空间

## 概述

混合检索能快速得到候选，但向量相似度仍是“分别编码后再比较”。对靠前候选，需要一个更细的模型同时阅读 query 与岗位文本。本模块用 Cross-Encoder 精排候选窗口，并把匿名案例空间作为有边界的辅助信号。

“Cross-Encoder”是把用户 query 和某个候选 JD 放进同一个模型输入中评分。它比单独比较两个向量更细，但调用成本更高，所以只作用于候选窗口。“双空间”则表示显式岗位空间与隐式案例空间同时提供信息：前者回答岗位文本是否匹配，后者回答相似匿名背景与岗位结果是否提供补充参考。

## 目标

- 使用环境配置的 `gte-rerank-v2` 对候选窗口精排。
- 记录实际请求窗口、预算裁剪后的有效窗口、是否应用和原因码。
- 运行期精排不可用时惰性回到同参数的非 Cross 基线，不伪装成已精排。
- 用匿名案例证据给显式候选有限加权，并随置信度收缩权重。
- 保持边界：隐式空间不能引入显式空间没有返回的岗位，也不能绕开 SQL 硬过滤。

## 数据流程

1. 混合检索先生成带显式分和 JD 证据的候选池。
2. 精排器读取候选的标题、必需技能和原始 JD，按字符与 token 预算裁剪 query 和文档。预算能容纳的前部候选构成 `applied_window`，未进入窗口的尾部保持原顺序。
3. DashScope 返回与输入一一对齐的相关性分数。客户端校验索引、数量、分数范围和非有限值，再按 Cross 分数重排窗口；尾部候选不参与这次外部评分。
4. 审计字段保存 requested、effective、applied 和 reason code。配置缺失属于启动或调用前错误；网络、超时、上游响应或预算导致的运行期不可用会触发惰性回退，并重新执行关闭 Cross 的同参数主链。
5. 显式检索与匿名案例检索并行。案例检索使用去标识后的简历字段，返回与候选岗位、公司和岗位族相关的历史结果证据。
6. 最终双空间分数采用 `(1-β) × 显式分 + β × 案例分`。β 由配置的最大权重再乘案例置信度得到；案例不足时权重自然缩小。案例空间失败时直接保留显式结果。

## 技术组成

- `app/llm/reranker.py`：`gte-rerank-v2` 客户端、输入预算、Semaphore、超时、有限重试和响应合同校验。
- `app/retrieval/hybrid_search.py`：候选窗口构造、`applied_window` 映射、Cross 排名落袋和惰性回退。
- `app/retrieval/dual_space_search.py`：显式与隐式并行、β 融合、稳定排序和显式结果兜底。
- `app/retrieval/implicit_search.py`：匿名案例 query 白名单、阶段结果加权、案例置信度和公开案例摘要。
- `anonymous_resume_cases` 与 `case_job_outcomes`：保存去标识案例表示和岗位结果，不保存可直接识别个人的检索文本。

## 工程创新点

第一，精排不是“开关打开就算成功”。系统记录实际生效窗口，并区分配置错误、预算不足和运行期不可用。论文可以说明真实应用范围，而不是只说明配置值。

第二，惰性回退保持同一批硬条件、软偏好和 RAPTOR 计划，只关闭失败的 Cross 通道。这样，回退结果仍是可解释的显式基线。

第三，隐式案例空间采用置信度收缩的 β 融合，而且只匹配显式候选。它提供经验信号，但不拥有候选生成权。

## 完成标志

- Cross 开启时，生效窗口内候选带 `cross_score` 和 `cross_rank`，审计字段如实记录 applied 状态。
- 运行期精排失败时返回同参数显式基线；配置错误不会被静默吞掉。
- 双空间结果能够同时保留 explicit、implicit、confidence 和 supporting cases。
- 隐式空间不可用时显式结果仍可返回；隐式证据不会新增不在显式候选集中的岗位。
- Cross 的离线消融已有版本化工件；匿名案例 β 融合的独立量化收益在本轮允许来源中没有单独报告，待测。

# 模块六：三 Agent 与 Supervisor Harness

## 概述

检索只负责找到岗位，不能独立完成“问清需求、解释匹配、给出事实受限的简历策略”。本模块把这三类工作分给意图、匹配和策略三个业务角色，再由 Supervisor 与确定性 Harness 做过程核查和发布前核查。

“Harness”可以理解为一组围绕 Agent 的固定检查点。它不靠模型自觉遵守规则，而是在输入、输出和发布边界用 Python 合同检查岗位 ID、证据、数量和状态。LangGraph 只负责编排节点、条件边和 checkpoint，不改变三个业务角色的职责。

## 目标

- 先通过多轮咨询收集求职目标、地点或远程意愿、签证需求和软偏好，再形成可确认的 Match Brief。
- Matching Agent 对 Top-K 候选生成岗位级解释，并只引用该候选真实携带的 JD 证据。
- Strategy Agent 输出技能差距、简历修改计划和职业路径，简历建议必须通过证据白名单。
- Supervisor 同时做语义核查和确定性核查，恢复动作有明确上限。
- 正式 run 的阶段状态、事件、结果和 checkpoint 能够持久化并支持同一 run 续跑。

## 用户交互与数据流程

1. 图外咨询引擎按模板、澄清、深挖或探索阶段推进。必需槽位未齐时先补槽位；每轮只合并允许字段。用户 finalize 后先得到 Brief 草案，只有明确确认 version 与 hash 后才创建 run。
2. Intent 角色把已确认的咨询状态整理为当前目标、长期方向、硬条件、软偏好和避开岗位。若咨询状态已经完整，正式运行可以复用已确认状态，避免重复询问。
3. Matching Agent 调用检索主链，对明确避开的岗位做过滤，并为 Top-K 候选并行生成简短解释。模型请求的证据编号要与候选允许证据取交集；若模型没有给出有效编号，则回到候选原有 JD 证据。
4. Strategy Agent 接收结构化简历、`R###`/`C###` 和岗位证据，生成差距、简历修改计划与路径。输出后，本地白名单只保留引用已知证据编号且字段合同正确的条目。
5. Supervisor 核查硬条件违反、结果数量、岗位 ID、JD 证据、简历证据和案例声称。确定性 Harness 在 Agent 输入、输出和发布前记录检查点。
6. 若覆盖不足或硬条件异常，流程可以触发受控重检索；若建议缺证据，可以触发受控修复。计数保存在 GraphState，条件边只允许在预算内回到指定节点，图级 recursion limit 作为最后保护。
7. 发布节点把内部 SharedState 投影为公开 ProductResult。完整 prompt、内部错误、未引用证据和私有状态不会直接暴露给前端。

## 技术组成

- `app/agents/consult_engine.py`：多轮咨询、槽位和阶段状态机。
- `app/agents/intent_agent.py`、`matching_agent.py`、`strategy_agent.py`：三套职责分离的业务 prompt 与普通异步函数。
- `app/agents/supervisor.py`：规划与最终语义核查、证据风险判断和有界修复。
- `app/agents/supervisor_harness.py`：不调用模型的输入、输出和发布合同检查。
- `app/graph/build.py` 与 `app/graph/runner.py`：StateGraph 节点、条件边、run 启动或续跑、同步持久化语义。
- PostgreSQL checkpointer：使用独立异步连接池保存 GraphState checkpoint；允许反序列化的类型有显式白名单。

## 工程创新点

第一，职责按“理解需求、解释岗位、制定策略”拆开，但共享同一结构化状态。它们不是三个微服务，也不靠自由对话互相传递不可检查的文本。

第二，模型核查与确定性门并存。模型适合判断语义缺口，Python 与 SQL 适合核对 ID、允许集合、证据编号和版本。两者互补，而不是让 Supervisor 一次模型调用承担全部责任。

第三，恢复路径在图上可见。重检索只回到检索节点，修复只处理允许修改的结果；checkpoint 保存的是同一 run 的可恢复状态，不是新的用户会话。

## 完成标志

- 咨询能够形成用户可读、可确认且带 version/hash 的 Match Brief。
- 三个业务角色都只写入 SharedState 中约定的字段，Matching 和 Strategy 输出通过证据白名单。
- Harness 能识别缺岗位 ID、缺 JD 证据、无效简历证据和发布条件不满足。
- 重检索与修复均有上限，不存在开放式业务循环。
- 同一 run 能从数据库快照与 checkpoint 继续；终态结果幂等读取。服务重启后自动重新调度未完成 run 不在当前能力内。

# 模块七：PM 咨询督导

## 概述

正式匹配阶段已有 Supervisor，但用户在前置咨询里也可能遇到停滞、信息已经足够却不知道下一步，或刚进入深挖时缺少方向确认。本模块让 PM 在少数明确时机介入，同时避免每轮都额外调用模型。

PM 督导分为 L1 和 L2。L1 是不调用模型的事实层，只判断“现在发生了什么”；L2 是教练层，把 L1 选中的原因和当前状态组织成一条简短 PM note。两层分开后，触发时机和预算不由模型自行决定。

## 目标

- 用确定性事实判断咨询进展，不让模型决定自己何时插话。
- 覆盖 `stagnation`、`finalizable` 和 `deepen_entry` 三类触发。
- 在并发请求下先预约预算，再调用 L2，避免同一预算被重复消费。
- L2 失败时保留已经成功提交的用户轮次和需求顾问回复。
- 成功 PM note 同时进入咨询转录和监督日志，并在群聊中显示。

## 用户交互与数据流程

1. 每轮咨询结束时，L1 计算槽位缺口、完整度变化、停滞连续值、澄清进度、当前阶段、是否可 finalize 和剩余预算。澄清轮会暂停停滞累计，避免用户认真补经历时被误判为没有进展。
2. 触发选择有固定优先级和去重规则：`finalizable` 表示信息已经足够且澄清目标耗尽；`stagnation` 表示连续没有实质进展；`deepen_entry` 表示刚进入深挖阶段。每轮、每类和总预算都有确定性限制。
3. 需要 L2 时，系统先生成 attempt ID，并把状态为 reserved 的 reservation 与用户轮次一起提交。CAS，也就是“数据库仍是刚才读到的版本时才允许合并”，用于避免并发轮次重复预约。
4. 预约成功后才调用 L2。输入只包含 L1 事实、公开职业画像和当前轮次，不包含无关私有状态。返回 note 包含文本和 `pass` 或 `advise` verdict。
5. 第二次原子合并把 reservation 单调推进到 succeeded 或 unavailable。成功时 note 进入当前转录条目的 `supervisor_notes`，并把 verdict 写入 `supervisor_log`；失败时记录 timeout、parse 或 service 原因。
6. 前端把成功 note 渲染为 PM 气泡。`finalizable` note 后可以直接出现整理确认单入口；即使 L2 没有成功，确定性兜底入口仍允许已经满足条件的用户继续。

## 技术组成

- `app/agents/consult_coach.py`：L1 事实、触发选择、reservation、L2 调用、终态合并和日志。
- `app/api/v1/sessions.py`：用户轮次与 reservation 的第一次 CAS，以及 L2 结果的第二次 CAS。
- `CareerState.consult_transcript`：每轮咨询文本及内嵌 `supervisor_notes`。
- `SharedState.coach_reservations` 与 `supervisor_log`：预算账本和审计记录。
- `frontend/src/v2/WorkbenchPage.tsx`：PM 气泡、finalizable 行动入口和无 note 时的确定性兜底。

## 工程创新点

第一，监督触发权留在 L1 规则层。L2 只能回应已经选定的触发原因，不能自行增加调用频率或扩大预算。

第二，reservation 采用“先占预算、后调模型”的顺序。外部调用即使超时或进程中断，这次尝试也有可审计状态，不会被当成从未发生而无限重试。

第三，fail-open 的范围被明确限定：PM 辅助失败不回滚用户轮次，但错误仍写入日志。它保证主咨询可继续，不表示上游错误被隐藏。

## 完成标志

- L1 能从真实状态生成事实记录，并且只在三类触发中选择一个允许项。
- 并发请求不能为同一轮重复占用 PM 预算；reservation 只能从 reserved 前进到终态。
- L2 成功时 note 和 verdict 同时进入转录与监督日志；失败时有原因码且用户轮次仍保留。
- 群聊能显示持久化 PM note，并保留 finalize 的确定性兜底入口。
- 冻结验收的含糊简历演示路径已依次覆盖三类触发，并记录预算消费；这证明机制链路可运行，不代表每个用户都会收到相同数量的 PM note。来源：`docs/validation/2026-08-07-batch9-acceptance.md`。

# 模块八：多人服务、群聊工作台与评估

## 概述

前七个模块只有被可靠地组织成多人可用的产品流程，才能完成毕业设计的主线。本模块负责认证与会话隔离、长任务提交与轮询、群聊工作台的公开投影，以及可复现的离线评估。

服务进程不把用户业务状态放进模块级可变对象。SharedState、简历版本、run、事件、结果和 checkpoint 都按标识写入 PostgreSQL。FastAPI 负责异步 HTTP 接口，asyncpg 连接池复用数据库连接，外部模型调用由 Semaphore 控制并发。

## 目标

- 让不同账号的 session 和 run 有清晰的所有权边界。
- 提供邮箱或短信 OTP 登录、Cookie 会话和可配置的账号会话配额。
- 用“提交任务后轮询”承载耗时匹配，并让刷新后的页面可以恢复咨询与 run 进度。
- 把咨询转录、PM note、Brief、运行进度和结果投影成一条群聊时间线。
- 用版本化数据和脚本计算检索指标、硬过滤准确率和解释证据忠实度。

## 用户交互与数据流程

1. 用户通过可用 OTP 通道登录。浏览器使用 HttpOnly Cookie 携带认证会话；后端依赖根据账号查找其会话和 run，非属主请求返回统一的不可见结果。
2. 创建 session 时，配额检查与插入在同一数据库事务中完成。额度不足时前端显示可聚焦、可关闭的提示；当前没有支付闭环。
3. 工作台把上传、简历档案确认、咨询 chips、澄清进度、PM note、Match Brief、运行播报、结果和反馈放进同一时间线。咨询转录按轮次读取，run conversation 按事件序列读取，再稳定拼接。
4. 用户批准 Brief 后创建 run。接口快速返回任务标识，后台执行 LangGraph；前端轮询状态、conversation 和 result。run 的公开 conversation 由持久化阶段、事件和允许字段确定性投影，不把完整 SharedState 直接交给浏览器。
5. 结果区按 Now Fit、Stretch Fit 和 Bridge Role 展示岗位，并提供 JD/简历证据、技能差距、简历修改计划和职业路径。移动端使用抽屉导航，证据抽屉和额度对话框包含焦点管理。
6. 评估脚本读取版本化 query、排名、标签和 manifest，计算 Precision@K、Recall@K、MRR 与 NDCG@K。P@5 的白话含义是前五个结果中相关岗位的比例；MRR 关注第一个相关岗位出现得有多靠前。

## 技术组成

- FastAPI v1 路由：认证、session、简历、咨询、Brief、run、conversation、result、explain 和反馈。
- PostgreSQL + asyncpg：账号、会话、SharedState、run、事件、结果、配额和业务状态持久化；LangGraph checkpoint 使用独立的异步 PostgreSQL 连接池。
- React + TypeScript 群聊工作台：TanStack Query 负责请求、轮询和缓存失效，公开 DTO 由 OpenAPI 类型生成链约束。
- `app/api/conversation_projector.py` 与结果 projector：把内部状态变成稳定、隐私收敛的群聊消息与结果结构。
- `app/evaluation/metrics.py`、`scripts/evaluate_demo_corpus.py` 和 `data/eval/demo_corpus_cross_v1/`：指标计算、四通道消融与版本化实验工件。

## 工程创新点

第一，产品界面不是把三个 Agent 做成三个页面，而是把角色交接、确定性检查点和恢复事件投影到同一群聊时间线。用户能看到协作过程，但看不到内部 prompt 和私有状态。

第二，状态持久化和公开投影分离。数据库保存恢复所需的完整业务状态；前端只接收任务所需字段。这让多人隔离、刷新恢复和证据抽屉可以同时成立。

第三，评估不只给一个总分。四通道消融把混合基线、RAPTOR、Cross-Encoder 和两者同开分开记录，manifest 同时记录标签方法、候选池和精排实际窗口。

## 评估结论与口径

在版本化四通道消融中，RAPTOR 与 Cross-Encoder 同开时，P@5 为 **0.920**，MRR 为 **1.000**。这两个数只能按本次实验的 within-pool 口径理解：相关性标签来自四个 run 候选池的 LLM 评审，未经人工复核；它们适合比较同一候选池内的检索通道，不代表真实求职结果，也不能外推为个人结果预测。来源：`data/eval/demo_corpus_cross_v1/` 与 `docs/validation/2026-08-06-cross-encoder-ablation.md`。

冻结验收记录为：pytest **642 passed**，Vitest **105/105**，Playwright **14/14**，全局冒烟 **32 passed、0 failed**。这些数字只描述该冻结代码基线的自动化与演示门禁，不等同于真实用户长期效果。来源：`docs/validation/2026-08-07-batch9-acceptance.md`。

## 完成标志

- 登录账号只能通过公开接口读取自己的 session 和 run；会话配额可配置并在并发创建时统一结算。
- 长任务能够提交、轮询、刷新恢复并读取终态结果；服务业务状态不依赖进程内用户对象。
- 群聊时间线能稳定呈现咨询、PM note、Brief、运行交接、受控恢复和结果行动入口。
- 评估脚本能够从版本化工件复算排名指标，manifest 能说明标签来源、候选池和精排是否实际应用。
- 冻结自动化门禁与全局冒烟通过；跨更长时间、更多真实岗位与人工标注数据的外部效果待测。
